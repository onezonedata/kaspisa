# Копия и восстановление базы

Правила А1–А13 — в `AGENTS.md` корня репозитория.

## Копия

1. Проверь `id -u`. Если результат 0, остановись (А9).
2. Проверь переменные оболочки (А13):

   ```
   bash -c 'compgen -e' | grep -E '^(KASPISA_DRY_RUN|KASPISA_VERSION|KASPISA_IMAGE_PREFIX|COMPOSE_PROFILES|COMPOSE_FILE|COMPOSE_ENV_FILES|POSTGRES_.*)$'
   ```

   Команду не заменяй на `compgen -e` без `bash -c`: в zsh она ничего не находит.

   Если вывод не пустой, попроси владельца перезапустить агента в новой оболочке. Значения не выводи.

3. Создай копию:

   ```
   make backup
   ```

   Код выхода должен быть 0.

4. Проверь файл: `ls -l backups/`. Должен появиться новый `manual-<метка>.dump` с правами `-rw-------`.
5. Вынос копии с сервера владелец делает сам, командой `scp` из `docs/deploy.md`, раздел 5. Копия и ключ хранятся отдельно друг от друга.

## Восстановление

Восстановление заменяет всю базу данными из копии. Агент его не запускает: ни `make restore`, ни `deploy/restore.sh`, и флаг `--yes` не используется никогда (А8).

6. Покажи владельцу список копий: `ls -lt backups/`. Назови файл, который предлагаешь.
7. Предупреди: всё, что записано после копии, пропадёт.
8. Если копия с другого сервера, владелец кладёт её в `backups/` и сам меняет строку `KASPISA_ENCRYPTION_KEY=` в `.env` в редакторе (А2). Без этого доступы продавцов не расшифруются.
9. Отдай владельцу команду для его терминала и не выполняй её сам:

   ```
   make restore FILE=backups/<имя>.dump
   ```

   Владелец вводит `yes` сам.

10. После восстановления владелец проверяет сервисы: `docker compose -f docker-compose.prod.yml ps`. Если скрипт сообщил «база в неизвестном состоянии», владелец повторяет команду с тем же файлом.
