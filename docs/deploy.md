# Установка и обновление kaspisa

Инструкция для владельца. Команды выполняются из корня репозитория kaspisa, если не сказано иначе.

Что не проверено на чистом сервере Linux, см. раздел «Что не проверено» в конце.

## Режимы

| Режим | Где стоит kaspisa | Как открыть интерфейс | Что опубликовано наружу |
|---|---|---|---|
| `local` | ваш компьютер | `http://localhost:3000` | только `127.0.0.1:3000` |
| `tunnel` (умолчание) | сервер | SSH-туннель или `tailscale serve` | только `127.0.0.1:3000` на сервере |
| `public` | сервер с публичным IPv4 | `https://ваш-домен` | Caddy на `0.0.0.0:80` и `0.0.0.0:443` |

Ограничения `public`:

- Домен указывает только на IPv4 (запись A). Запись AAAA не ставьте: режим не поддерживает IPv6, и все клиенты через шлюз окажутся с одним адресом.
- Нужен Docker Engine 28 или новее (проверяет `install.sh`). Rootless Docker не поддерживается.
- Порты 80 и 443 должны быть доступны из интернета: без 80 Let's Encrypt не выпустит сертификат.
- Регистрация снаружи закрыта: `/register` отвечает 404. Первая учётная запись заводится через SSH-туннель (раздел «Первая учётная запись»), после неё регистрацию закрывает сам сервер (раздел «Регистрация, сотрудники, ссылка на исходный код»).
- Docker публикует порты в обход ufw. Защита сервера — в том, какие порты опубликованы (`docker-compose.prod.yml`), а не в правилах ufw.

## Что понадобится

- Репозиторий kaspisa на машине, где ставите (`git clone <адрес>`; пути установки и адрес — в `docs/install.md`).
- `git`, `make`, `bash`, Docker с плагином compose (`docker compose version`).
- Для `update.sh` в режиме сборки (см. раздел «Обновление») дополнительно `uv` и Node.js 24 с npm: скрипт запускает `make setup`, `make lint` и `make test-backend`. Google Chrome нужен только для `bash update.sh <версия> --full-tests` (полный `make test` с e2e-тестами Playwright, `channel: chrome`) — тем, кто сам правит код. `deploy/prepare-server.sh` их не ставит. `update.sh` проверяет `uv`, `node` и `npm` до слияния; Chrome не проверяет.
- Без root (проверено на Ubuntu 24.04): `uv` (на стенде 0.13.5) и Node (24.22.3) — официальные архивы в `~/.local`, с проверкой sha256 и SHASUMS256 соответственно. На Ubuntu `~/.profile` сам добавляет `~/.local/bin` в PATH: после установки нужен новый вход. Chrome ставится от root из репозитория Google (`google-chrome-stable`).

## 1. Подготовка сервера

На чистом Ubuntu или Debian от root:

```
sudo bash deploy/prepare-server.sh            # tunnel и local
sudo bash deploy/prepare-server.sh --public   # плюс порты 80 и 443
sudo bash deploy/prepare-server.sh --tailscale  # плюс Tailscale (по флагу)
```

Скрипт ставит Docker Engine с плагином compose, ufw и (по флагу) Tailscale. Порты SSH он берёт у работающего sshd (`sshd -T`, `ssh.socket`), а не предполагает 22. Если порт определить не удалось, ufw не включается и скрипт завершается с кодом 1.

- Перед включением ufw откройте второй терминал и проверьте, что SSH работает. Потеря доступа к серверу здесь возможна.
- Tailscale скрипт не входит: выполните `sudo tailscale up` сами и пройдите вход по ссылке.
- Чтобы запускать `docker` без sudo, добавьте себя в группу: `sudo usermod -aG docker $USER`, затем войдите заново. Через sudo установку не запускайте: копии получат владельца root.
- SSH по ключу, смена порта, fail2ban и автообновления системы в этот документ не входят: см. `docs/install.md`, раздел «Защита сервера».

## 2. Установка

```
bash install.sh local
bash install.sh tunnel
KASPISA_DOMAIN=kaspisa.example.com KASPISA_CADDY_TLS=you@example.com bash install.sh public
```

Без аргумента в терминале установщик спросит режим (по умолчанию `tunnel`). Для `public` домен и значение `KASPISA_CADDY_TLS` берутся из окружения или спрашиваются. `KASPISA_CADDY_TLS` — ваш e-mail (Let's Encrypt) или `internal` (внутренний центр Caddy, браузер покажет предупреждение; только для проверки).

Что делает `install.sh`:

1. Проверяет `docker compose`, доступ к демону Docker и (для `public`) версию Docker Engine 28+. Если проверка не прошла, `.env` не создаётся.
2. Создаёт `.env` с правами 600: ключ шифрования, три пароля базы, режим, версию. Значения секретов не печатает.
3. Собирает образы (первый раз это несколько минут) и поднимает сервисы.

Повторный запуск `.env` не меняет. Смена режима через установщик не предусмотрена: он откажет, если режим в `.env` другой.

Файл `.env` не передавайте никому и не вставляйте в чат, issue или отчёт. Не открывайте его в местах, где экран видят другие.

## 3. Первая учётная запись

Способ входа зависит от режима:

- `local`: откройте `http://localhost:3000/register`.
- `tunnel`: на своём компьютере `ssh -L 3000:127.0.0.1:3000 <сервер>`, затем `http://localhost:3000/register`. Вариант через Tailscale: `tailscale serve --bg 3000` на сервере и адрес `*.ts.net` из вывода команды (не проверено, см. ниже).
- `public`: снаружи регистрация закрыта. Заводите учётную запись через туннель: `ssh -L 3000:127.0.0.1:3000 <сервер>`, затем `http://localhost:3000/register`. Сотрудников добавляйте на странице «Пользователи» (раздел «Регистрация, сотрудники, ссылка на исходный код»).

После этого войдите в интерфейс обычным адресом (`https://ваш-домен` в `public`).

## 4. Ключ шифрования

Ключ `KASPISA_ENCRYPTION_KEY` в `.env` шифрует доступы продавцов к кабинетам Kaspi. В копии базы доступы зашифрованы этим ключом. Без ключа копия даёт данные магазинов, но сами доступы не расшифровать: магазины придётся подключать заново.

Показать ключ можно только в своём терминале:

```
make show-key
```

- Запускайте в обычном терминале, не через агентов, скрипты и чаты. Вывод остаётся в прокрутке терминала, в tmux и screen, а также в записи сеанса.
- Скопируйте ключ в менеджер паролей, затем очистите экран и историю: `clear`, в tmux — `clear-history`.
- Храните ключ отдельно от копий: не в той же папке, не на том же диске и не в том же архиве, что `backups/`.
- Установщик создаёт новый ключ при первой установке. Потерянный ключ не восстанавливается.

## 5. Копии базы

Сервис `backup` делает копии сам. Раз в час он проверяет, нужна ли суточная копия, и снимает её, если последняя старше 24 часов. Копии лежат в `backups/` в корне репозитория (каталог 700, файлы 600).

| Класс | Имя файла | Когда | Хранится |
|---|---|---|---|
| суточная | `daily-<метка>.dump` | раз в сутки | 7 последних |
| ручная | `manual-<метка>.dump` | `make backup` | 3 последних |
| перед обновлением | `update-<метка>.dump` | каждый `update.sh` | 3 последних |

Ротация идёт внутри класса: обновления не вытесняют ручные копии. Сроки хранения — в таблице выше. Вынос копий с сервера — вручную, автоматики нет.

- Ручная копия: `make backup`.
- В копии только база. В ней нет `.env`, ключа и Redis. Доступы Kaspi там зашифрованы.
- `backups/` сервер не выносит. Перенесите копию сами, например: `scp <сервер>:<путь к репозиторию>/backups/daily-<метка>.dump ~/kaspisa-копии/`.

### Восстановление

Восстановление заменяет всю базу данными из копии. Всё, что записано после копии, пропадёт.

1. Если копия с другого сервера, положите её в `backups/`. Имя должно начинаться с `daily-`, `manual-` или `update-` и заканчиваться `<метка>.dump`.
2. Если ключ на новом сервере другой, замените строку `KASPISA_ENCRYPTION_KEY=` в `.env` на сохранённый ключ (в редакторе, без вывода в терминал). Без этого восстановленные доступы не расшифруются.
3. Выполните:

   ```
   make restore FILE=backups/<имя>.dump
   ```

   Введите `yes`. Скрипт остановит api и worker, заменит базу, применит миграции (копия старой версии поднимется до текущей схемы) и запустит сервисы.
4. Если скрипт сообщил «база в неизвестном состоянии», api и worker остановлены. Повторите команду из шага 3 с тем же файлом.

## 6. Обновление

Если образы выпуска не опубликованы в GHCR, обновление идёт из git: режим сборки.

```
bash update.sh <метка или ветка>
```

Ветка: `bash update.sh <ветка>` сливает `origin/<ветка>` (раньше сливалась локальная ветка, и обновление по ветке ничего не приносило). Если ветка и метка называются одинаково, берётся метка.

Перед запуском:

- `git status` должен быть пустым (`.env` и `backups/` в `.gitignore`).
- Запускайте в tmux, чтобы видеть вывод и не потерять его при обрыве SSH. Ждите конца в том же сеансе tmux, а не опросом по SSH циклом.
- Журнал команд пишется в `backups/update-<метка времени>.log` (права 600). В терминал выводятся короткие сообщения.

В режиме сборки скрипт сливает версию, запускает `make lint` и тесты бэкенда `make test-backend`, в том числе свойства «цена в границах» (с `--full-tests` — полный `make test` с vitest и e2e, для тех, кто правит код: случайное падение тестов интерфейса не должно откатывать обновление) (тестовая база поднимается отдельно; порты — `KASPISA_PG_PORT` и `KASPISA_REDIS_PORT`, если заняты), собирает образы. Затем он останавливает api и worker, делает копию `update-*`, применяет миграцию, поднимает новые api и web и worker с `KASPISA_DRY_RUN=true` на 60 секунд. Потом поднимает worker со значением из `.env`, записывает версию в `.env`.

Во время обновления api и worker остановлены. Интерфейс может быть недоступен.

Учтите: в режиме сборки обновление откатывается при любом упавшем тесте. При проверке на чистом сервере так откатились три прогона из четырёх, в том числе из-за случайных падений тестов (с тех пор исправлены). Повторный запуск `update.sh` безопасен: откат возвращает прежнюю версию.

Режим реестра (`KASPISA_IMAGE_PREFIX` задан в `.env`) — `bash update.sh vX.Y.Z`: файлы переключаются на метку, образы скачиваются. Приёмка проверяла этот режим с локально собранными образами под префиксом; скачивание из GHCR не проверено.

Коды выхода:

- `0` — готово, работает новая версия.
- `1` — обновление не удалось, работает прежняя версия (откат выполнен). Причина — в журнале.
- `2` — откат не удался или `.env` не записан. Нужны ручные шаги ниже.

### Откат

Откат выполняется сам на любом сбое до сообщения «Готово». Он возвращает git к прежней версии. Если миграция прошла, база восстанавливается из `update-*`, созданной в этом запуске. Если миграция упала и схема не изменилась, база не трогается.

После сообщения «Готово» автоматического отката нет: новый worker мог записать цены. Откат после этого момента описан только как ручные шаги ниже и не проверен.

### Ручные шаги после сбоя

Нужны, если update.sh завершился с кодом 2 или прервался SIGKILL или выключением питания. Остановите update.sh и не запускайте его заново, пока не выполните шаги.

1. Посмотрите последний журнал: `ls -t backups/update-*.log | head -1`, затем `less` на него.
   Если журнал не содержит «Готово», но прошло больше 60 секунд после строки «Запускаю worker (60 с без записи цен)», боевой worker с записью мог уже быть запущен. Тогда **базу не восстанавливайте**: новый worker мог записать цены. Проверьте в чистой оболочке журнал worker (`docker compose -f docker-compose.prod.yml logs --tail 50 worker`) и, если он работает новой версией, впишите `KASPISA_VERSION=<результат git describe --tags --always>` в `.env`. Остальные шаги пропустите: откат здесь вреден.
2. Проверьте, что процесса update.sh нет: `ps aux | grep update.sh`.
3. Снимите блокировку (только если процесса нет): `rm -rf backups/.lock.d`. Сообщение блокировки назовёт процесс, который её держит.
4. Верните git к версии до обновления: `git reflog -n 10` покажет прежний HEAD, затем `git reset --hard <прежний HEAD>`. Если висит слияние, сначала `git merge --abort`.
5. Если миграция прошла (схема новая), восстановите последнюю копию `update-*`: `make restore FILE=backups/update-<метка>.dump`. Пока `.env` содержит прежнюю версию, это вернёт базу в прежнюю схему.
6. Поднимите сервисы в чистой оболочке (см. раздел «Переменные оболочки»): `docker compose -f docker-compose.prod.yml up -d --no-build --wait`.
7. Войдите в интерфейс и проверьте версию.

Шаги 4–6 не проверены на стенде: SIGKILL не проверялся.

## 7. Проверка новой версии

Установка может сообщать о новой версии в интерфейсе (плашка). Проверка делает запрос к GitHub Releases не чаще раза в сутки.

- `install.sh` записывает `KASPISA_UPDATE_REPO=onezonedata/kaspisa`: проверка включена.
- Чтобы выключить, оставьте значение пустым; если ставите свою доработку — укажите свой `владелец/репозиторий`. Затем перезапустите api (команда ниже).
- Проверка только сообщает о версии. Обновляет вас `update.sh`.

После правки `.env` перезапустите api в чистой оболочке: `docker compose -f docker-compose.prod.yml up -d --no-build api`.

## 8. Запись цен

После установки в `.env` стоит `KASPISA_DRY_RUN=true`. Обработчик считает цены и пишет решения в журнал, но не отправляет их в Kaspi.

- Включать запись — ваше решение. Измените `KASPISA_DRY_RUN=false` в `.env` и перезапустите worker: `docker compose -f docker-compose.prod.yml up -d --no-build worker` в чистой оболочке.
- Условия договора Kaspi о работе через сессию кабинета не изучены. Запись в Kaspi — на ваш риск.
- Ограничение частоты запросов к kaspi.kz — 1 запрос в секунду на установку, пока не выполнен замер.

## 9. Переменные оболочки и `.env`

Значения установки берутся только из `.env`. Скрипты `install.sh`, `update.sh` и `restore.sh` снимают из окружения оболочки переменные `KASPISA_*`, `POSTGRES_*`, `COMPOSE_PROFILES`, `COMPOSE_FILE`, `COMPOSE_ENV_FILES` при каждом вызове `docker compose`. Так `KASPISA_DRY_RUN=false bash install.sh` не переключит запись, если `.env` уже создан.

- Ручные команды `docker compose` такой защиты не имеют. Запускайте их в новой оболочке или после `unset` всех этих переменных, и всегда с `-f docker-compose.prod.yml`: без него compose возьмёт файл разработки.
- Команда `make backup` вызывает compose напрямую, без этой защиты. Запускайте её в чистой оболочке.
- Порты и подсеть после установки меняйте строкой в `.env`: `KASPISA_WEB_PORT`, `KASPISA_HTTP_PORT`, `KASPISA_HTTPS_PORT`, `KASPISA_EDGE_SUBNET`. Переменные оболочки на работающую установку не действуют. Но при первом создании `.env` `install.sh` берёт эти четыре значения и `COMPOSE_PROJECT_NAME` из окружения (так делают приёмочные проверки); для обычной установки оставьте их пустыми.
- Подсеть `edge` должна совпадать с `KASPISA_EDGE_SUBNET` в `.env`. Скрипты проверяют это перед каждым запуском. Если не совпадает, они выходят с кодом 1 и сообщают, что нужно пересоздать сеть. Пересоздание — в чистой оболочке:

  ```
  docker compose -f docker-compose.prod.yml down
  ```

  Тома с данными не удаляются. После этого повторите команду, которая завершилась ошибкой.

## Что не проверено

Этот документ описывает поведение, которое проверено не полностью:

- Установка на Debian 12 и Ubuntu 22.04 не выполнялась; на чистом Ubuntu 24.04 проверена. Ранняя проверка шла на Docker Desktop (macOS).
- Настоящий адрес клиента за Caddy на Linux не проверен. На Docker Desktop адрес подменяется адресом шлюза, поэтому лимиты по IP там не отражают реальных клиентов.
- Let's Encrypt не проверен: проверка шла с `tls internal`.
- Tailscale и `tailscale serve` не проверены.
- Клон с GitHub: при проверке публичного репозитория ещё не было, доставка шла через git bundle; сеть до GitHub с сервера не проверена.
- arm64 проверен только через QEMU, не на настоящем железе.
- Требование Docker Engine 28+ по первоисточнику (moby #45610) не сверено.
- Устойчивость к SIGKILL и потере питания при обновлении не проверена; ручные шаги выше не выполнялись на стенде.
- Лимит частоты kaspi.kz не замерен.

## Регистрация, сотрудники, ссылка на исходный код

- После первой учётной записи регистрация закрыта: страница регистрации показывает «Регистрация закрыта». Закрывает её сам сервер, Caddy — второй слой.
- Сотрудников добавляет и удаляет администратор — первая учётная запись установки, — на странице «Пользователи». Администратор в учётной записи один; передать роль в интерфейсе нельзя. Добавление и удаление просят повторный пароль администратора.
  - Добавление: введите e-mail сотрудника. Страница один раз покажет ссылку для задания пароля (`/reset-password#token=…`); она действует 1 час. Передайте её сотруднику лично, не в общий чат. Открывайте ссылку на своём устройстве: на общем компьютере после задания пароля очистите историю браузера, потому что `#token=…` остаётся в ней до истечения часа. Ссылку нельзя получить повторно: если она истекла, удалите пользователя и добавьте снова. Добавлять можно не больше 20 раз в час.
  - Удаление: кнопка «Удалить» в строке пользователя; все его входы завершаются, записи журнала действий с его адресом остаются. Себя удалить нельзя.
  - Изменить или отключить уведомления Telegram и удалить магазин может только администратор.
- Если интерфейс недоступен, сотрудника можно добавить аварийной командой, в чистой оболочке (раздел «Переменные оболочки и `.env`»):

  ```
  docker compose -f docker-compose.prod.yml exec api python -m kaspisa.api.add_user <ваш e-mail> <e-mail сотрудника>
  ```

  Команда печатает токен (не ссылку). Сотрудник открывает `/reset-password`, вводит токен и задаёт пароль в течение часа. Команда создаёт обычного пользователя, а не администратора.
- Забытый пароль, в том числе администратора, восстанавливается только командой `docker compose -f docker-compose.prod.yml exec api python -m kaspisa.api.reset_token <e-mail>`: она печатает токен, пользователь задаёт новый пароль на странице `/reset-password`.
- Команды `add_user` и `reset_token` запускайте сами в своём терминале: токен даёт вход в учётную запись, не передавайте его помощнику-агенту и в чат. Агент-установщик их не запускает (правило А7 в `AGENTS.md`), а отдаёт вам текстом.
- Если администратором стал не тот. При обновлении до версии с ролями администратором становится первый по времени создания пользователь учётной записи; миграция печатает его адрес, а `update.sh` сохраняет вывод в журнал обновления (`grep "администратор арендатора" backups/update-*.log`). Если роль досталась не тому, смените её вручную в одной транзакции: сначала снимите флаг со старого администратора, затем поставьте новому (иначе сработает индекс «не больше одного администратора»). Подставьте адрес нового администратора:

  ```
  docker compose -f docker-compose.prod.yml exec db psql -U postgres -d kaspisa -v ON_ERROR_STOP=1 <<'SQL'
  BEGIN;
  UPDATE app_user SET is_admin = false
    WHERE is_admin AND tenant_id = (SELECT tenant_id FROM app_user WHERE email = '<новый e-mail>');
  UPDATE app_user SET is_admin = true WHERE email = '<новый e-mail>';
  COMMIT;
  SQL
  ```

  После этого старый администратор должен выйти и войти заново (роль читается из базы при каждом запросе, но сессии лучше начать заново): страница «Выйти на всех устройствах» или `reset_token` и новый пароль.
- Ссылка на исходный код внизу страниц обязательна по AGPL-3.0, §13. Она собирается в `frontend/src/lib/source.ts` из двух частей: `SOURCE_HREF = SOURCE_REPO_URL + "/tree/v" + версия`. Если вы изменили код и даёте им пользоваться другим, укажите свой репозиторий в `SOURCE_REPO_URL` и пересоберите образ. Форк без меток правит обе константы: `SOURCE_REPO_URL` и `SOURCE_HREF`; одной `SOURCE_REPO_URL` мало, ссылка `/tree/v0.1.0` будет битой. Если в вашем репозитории нет метки `v<версия>`, поменяйте `SOURCE_HREF` на адрес, где лежит именно запущенный код.
- Сборка из `main` между выпусками (режим сборки `update.sh`) показывает метку последней версии из `frontend/package.json`, а запущенный код новее. Для §13 такая ссылка неточна. Если вы даёте пользоваться такой сборкой другим, укажите в `SOURCE_HREF` ветку или коммит, из которого собран образ.
