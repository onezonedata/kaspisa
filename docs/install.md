# Установка kaspisa

Инструкция для владельца и для его агента. Эксплуатация (режимы, копии, обновление, ключ) — в `docs/deploy.md`. Команды выполняются из корня репозитория, если не сказано иначе.

Адрес репозитория: `https://github.com/onezonedata/kaspisa`.

## Что нужно знать до установки

- Установкой владеет один владелец: он отвечает за неё и за доступы.
- Одна установка — один магазин Kaspi. Несколько магазинов — несколько установок.
- Запись цен по умолчанию выключена (`KASPISA_DRY_RUN=true`). Включает её владелец сам, см. `docs/deploy.md`, раздел 8.
- Пароли кабинетов Kaspi, ключ шифрования и файл `.env` не передавайте никому и не вставляйте в чат, issue или отчёт.
- kaspisa распространяется по лицензии AGPL-3.0 (файл `LICENSE`). Условия использования и отказ от ответственности — `TERMS.md`; текст помечен как черновик до проверки юристом.
- Установка на чистом Ubuntu 24.04 проверена, другие системы — нет. Непроверенное — в конце этого документа.

## Требования к серверу

Проверено на чистом Ubuntu 24.04: 1 vCPU, 4 ГБ памяти (на стенде 3,9 ГБ доступно), 20 ГБ диска, без swap.

- Установка (`install.sh tunnel`): около 6 минут, пик памяти 1,4 ГБ, диск с 3,6 до 7,2 ГБ. Минимум: 1 vCPU, 4 ГБ, 20 ГБ.
- Обновление в режиме сборки (`update.sh`, `docs/deploy.md`): при проверке с полным набором тестов — 11–13 минут, пик памяти 2,3 ГБ, диск до 11 ГБ; по умолчанию теперь идут только тесты бэкенда, так что быстрее. Рекомендуется 2 vCPU, 4 ГБ, 30 ГБ: на 4 ГБ запас около 1,6 ГБ.

Ubuntu 22.04 и Debian 12 на этом стенде не проверялись.

## Четыре пути

Выберите один:

1. Локально: на своём компьютере.
2. Сервер одной командой: чистый Ubuntu (проверено на 24.04) или Debian, вход под root.
3. Через агента: Claude Code, Codex или OpenCode ставит и ведёт установку по инструкции из репозитория.
4. С помощью автора: вы делаете сами, а вопросы задаёте через Issues.

Режимы (`docs/deploy.md`, раздел 2): `local` — ваш компьютер; `tunnel` — сервер, интерфейс открывается через SSH-туннель (по умолчанию); `public` — сервер с публичным IPv4 и доменом.

## 1. Локально

Нужны `git`, `make`, `bash`, Docker с плагином compose (`docker compose version`).

```
git clone https://github.com/onezonedata/kaspisa
cd kaspisa
bash install.sh local
```

Откройте `http://localhost:3000/register` и заведите учётную запись. Ключ шифрования покажите в своём терминале: `make show-key`. Сохраните его отдельно от копий (`docs/deploy.md`, раздел 4).

## 2. Сервер одной командой

Для входа под root на чистом Ubuntu или Debian. Установка всё равно идёт от пользователя `kaspisa`, а не от root.

Перед строкой:

- Проверьте, что вход по SSH работает и что вы можете открыть второе окно.
- Если на сервере есть `/root/.ssh/authorized_keys`, строка скопирует его пользователю `kaspisa`. Если файла нет, ключа для `kaspisa` не будет: до закрытия сессии root добавьте свой публичный ключ в `~kaspisa/.ssh/authorized_keys` (права 600). Иначе войти под `kaspisa` по SSH нельзя.

Строка (для режима `tunnel`):

```
apt-get update && apt-get install -y git make && adduser --disabled-password --gecos '' kaspisa && { [ ! -f /root/.ssh/authorized_keys ] || { install -d -m 700 -o kaspisa -g kaspisa ~kaspisa/.ssh && install -m 600 -o kaspisa -g kaspisa /root/.ssh/authorized_keys ~kaspisa/.ssh/; }; } && su - kaspisa -c 'git clone https://github.com/onezonedata/kaspisa kaspisa' && bash ~kaspisa/kaspisa/deploy/prepare-server.sh && usermod -aG docker kaspisa && su - kaspisa -c 'cd kaspisa && bash install.sh tunnel'
```

Что делает строка по порядку:

1. Ставит `git` и `make`.
2. Создаёт пользователя `kaspisa` без пароля и без `sudo`.
3. Копирует ключи root пользователю `kaspisa`, если они есть.
4. Клонирует репозиторий от имени `kaspisa`.
5. Готовит сервер: Docker, ufw с фактическими портами SSH (`deploy/prepare-server.sh`).
6. Добавляет `kaspisa` в группу `docker`.
7. Ставит kaspisa от имени `kaspisa`.

Для режима `public`: в пятом шаге `prepare-server.sh --public`, в седьмом — `su - kaspisa -c 'cd kaspisa && KASPISA_DOMAIN=<домен> KASPISA_CADDY_TLS=<e-mail> bash install.sh public'`. Переменные передаются внутри `-c`, потому что `su -` очищает окружение.

Если вход на сервер у вас под обычным пользователем с `sudo`, а не под root:

```
git clone https://github.com/onezonedata/kaspisa
cd kaspisa
sudo bash deploy/prepare-server.sh
sudo usermod -aG docker $USER
```

Войдите заново и выполните `bash install.sh tunnel`. Через `sudo` саму установку не запускайте: копии получат владельца root.

Почему не от root: контейнеры шли бы с uid 0, копии принадлежали бы root, а агент получил бы root. Оговорка: группа `docker` равносильна root на хосте. Отдельный пользователь защищает от случайностей, а не от намеренного обхода.

После установки, с вашего компьютера:

```
ssh -L 3000:127.0.0.1:3000 kaspisa@<сервер>
```

Если в вашем `~/.ssh/config` для этого сервера задан другой `User`, пишите пользователя явно: `ssh -L 3000:127.0.0.1:3000 -l kaspisa <сервер>` (или `kaspisa@<сервер>`). Если порт SSH изменён (см. «Защита сервера», п. 2), добавьте `-p <порт>`.

Откройте `http://localhost:3000/register`. Ключ шифрования: в своём терминале на сервере — `su - kaspisa -c 'cd kaspisa && make show-key'`.

После первой учётной записи регистрация закрывается. Сотрудников добавляет владелец в интерфейсе на странице «Пользователи» (`docs/deploy.md`, раздел «Регистрация, сотрудники, ссылка на исходный код»). Аварийная команда `add_user` печатает токен; агент её не запускает.

### Защита сервера

Команды этого раздела выполняет владелец от root. Агент, запущенный под `kaspisa`, их не выполняет: он готовит их по скиллу `.claude/skills/kaspisa-server/SKILL.md`. Держите консоль хостера под рукой: если вход по SSH пропадёт, это единственный способ попасть на сервер. Проверьте, что в консоли есть рабочий вход (на образах без пароля консоль бесполезна).

Порядок:

1. Вход по ключу. Проверка перекрывающих `Match`/`AllowUsers` в sshd, файл `/etc/ssh/sshd_config.d/00-kaspisa.conf` с `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`; `sshd -t`; `sshd -T -C …`; перезапуск службы только после этого, при открытой второй сессии.
2. Смена порта SSH (по желанию). Новый порт — в ufw и в fail2ban, затем sshd слушает оба порта, вход проверяется вторым окном, и только после подтверждения удаляется старый порт. Подробный порядок — в скилле.

   На Ubuntu 24.04 порт задаёт `ssh.socket`. Строки `Port` в `/etc/ssh/sshd_config.d/00-kaspisa.conf` генератор `sshd-socket-generator` сам переносит в сокет после `systemctl daemon-reload`; затем `systemctl restart ssh.socket`. Ручной override не нужен. У хостера может быть свой сетевой фильтр: откройте новый порт и там до удаления старого.
3. Автообновления: `apt-get install -y unattended-upgrades` и `dpkg-reconfigure -f noninteractive unattended-upgrades`. Без автоматической перезагрузки. Проверьте два файла: в `/etc/apt/apt.conf.d/20auto-upgrades` есть строка `APT::Periodic::Unattended-Upgrade "1";`, в `/etc/apt/apt.conf.d/50unattended-upgrades` строка `Unattended-Upgrade::Automatic-Reboot` равна `"false"` или закомментирована. На Ubuntu по умолчанию ставятся только обновления безопасности. На Debian 12 стандартный файл включает ещё источник `label=Debian` — обновления точечных выпусков; их оставляем.
4. fail2ban: `apt-get install -y fail2ban` и `/etc/fail2ban/jail.d/kaspisa.local` с включённым jail `sshd`, `backend = systemd` и фактическим портом.
5. Уведомление о входе по SSH через Telegram.

Для уведомления создайте бота сами. Создайте файл сразу с нужными правами: `install -m 600 -o root -g root /dev/null /etc/kaspisa-ssh-notify.curl`. Затем впишите в него редактором (не через `echo`: токен попадёт в историю оболочки):

```
url = "https://api.telegram.org/bot***/sendMessage"
data = "chat_id=***"
```

Строка `data` начинается с `chat_id=`: без этого префикса Telegram отвечает `chat_id is empty`. Номер группы начинается с минуса (`-100…`), это нормально. Проверка, которая не печатает токен (видно только `"ok"`):

```
curl -sS --max-time 5 -K /etc/kaspisa-ssh-notify.curl --data-urlencode "text=проверка" | grep -o '"ok":[a-z]*'
```

Сообщение приходит на каждый сеанс SSH, включая туннель и сеансы агента. Агенту не давайте опрашивать сервер частыми SSH-командами: каждый вход даёт сообщение.

Скрипт создайте так же: `install -m 755 -o root -g root /dev/null /usr/local/sbin/kaspisa-ssh-notify`, затем впишите текст редактором. Владелец скрипта — root: если его сможет править пользователь `kaspisa`, через `pam_exec` он получит root.

```
#!/bin/bash
# Сообщение о входе по SSH: вызывается pam_exec, всегда завершается с кодом 0.
[ "${PAM_TYPE:-}" = open_session ] || exit 0
text="Вход по SSH: пользователь ${PAM_USER:-?}, адрес ${PAM_RHOST:-?}, $(date '+%Y-%m-%d %H:%M:%S %Z')"
curl -sS --max-time 5 -K /etc/kaspisa-ssh-notify.curl --data-urlencode "text=$text" >/dev/null 2>&1 &
exit 0
```

В `/etc/pam.d/sshd` добавьте строку `session optional pam_exec.so /usr/local/sbin/kaspisa-ssh-notify`. Известное ограничение: сообщение приходит на каждый сеанс, включая `scp`, туннель и сеансы агента.

## 3. Через агента

Агент — Claude Code, Codex или OpenCode. Он читает правила из `AGENTS.md` в корне репозитория и ставит kaspisa по скиллам из `.claude/skills/`.

Где запускать: предпочтительно на сервере, под пользователем `kaspisa`, в папке репозитория. Агент на вашем компьютере, который работает с сервером через SSH, защищён только текстом правил: файлы на сервере его настройки не ограничивают.

Токены облачного провайдера, Tailscale и Telegram скиллам не нужны: облако, Tailscale и бота вы настраиваете сами. Если токен нужен для ваших команд, задайте его в окружении своего терминала, вне сеанса агента, и не вставляйте в чат. Не экспортируйте токены в терминал, из которого запускаете агента: агент видит своё окружение. Если токен всё же нужен агенту, берите токен с узкими правами и коротким сроком и отзовите его после работы.

Примеры фраз для агента:

- «установи kaspisa в режиме tunnel»;
- «сделай копию базы»;
- «обнови kaspisa до v0.0.2»;
- «подготовь команды для защиты сервера по скиллу kaspisa-server».

Чего агент не делает (правила А1–А9 простыми словами):

- не читает и не меняет `.env`;
- не включает запись цен и не переводит магазин в режим `live`;
- не просит, не принимает и не использует пароль Kaspi;
- не просит токены и не печатает переменные окружения;
- не показывает ключ шифрования (`make show-key`);
- не запускает `add_user` и `reset_token`: они печатают токен входа;
- не восстанавливает базу из копии;
- не работает под root.

Что делаете вы сами:

- туннель и регистрацию учётной записи;
- подключение магазина: пароль Kaspi — только в интерфейсе;
- `make show-key` в своём терминале;
- включение записи цен (`docs/deploy.md`, раздел 8);
- восстановление: команду запускаете сами и вводите `yes`;
- шаги защиты сервера от root.

Не запускайте агента-установщика в режиме без подтверждений: `--dangerously-skip-permissions` или режим `bypassPermissions` в Claude Code, `--yolo` или `--dangerously-bypass-approvals-and-sandbox` в Codex, разрешение `allow` для bash в OpenCode. Подтверждение команд — главный слой защиты: без него команда, которая печатает ключ, выполняется без вопроса. В Claude Code этот режим в папке репозитория выключен настройкой `disableBypassPermissionsMode` в `.claude/settings.json`: флаг молча не действует, сессия идёт с обычными подтверждениями (проверено на Claude Code 2.1.304). Настройка, запреты и хук действуют, только если агент запущен из корня репозитория. На Codex и OpenCode эта настройка не действует.

Что даёт каждый агент:

- Claude Code: правила `AGENTS.md`, запреты в `.claude/settings.json` и хук `.claude/hooks/kaspisa-guard.sh`. Хук проверяет только команды оболочки и отклоняет их по тексту. В обычном режиме разрешений без вашего подтверждения агент выполняет только команды из разрешённого списка. Не подтверждайте запросы не глядя. Разрешённый список Claude Code применяет только после того, как вы приняли диалог доверия к папке; до этого он спрашивает подтверждение и на команды из списка (например, `git status`). Запреты `deny` и правило `ask` действуют сразу.
- Codex: читает `AGENTS.md`; файлов настроек Codex в репозитории нет. Защита держится только на правилах `AGENTS.md`. Песочницу Codex настраиваете сами по его документации. Профили и правила Codex в документации помечены как beta и experimental, поэтому запрет на `.env`, созданный уже после запуска агента, и запрет команд вне песочницы не гарантированы.
- OpenCode: читает `AGENTS.md` и `.claude/skills/`. Защита — правила `AGENTS.md` и встроенный запрос на чтение файлов: на запрос чтения `.env` отвечайте «нет». Команды оболочки вроде `cat .env` ничем не закрыты, кроме правил.

Честное ограничение: правила, `deny` и хук — дополнительный слой, а не граница безопасности. Агент работает от того же пользователя, которому принадлежит `.env`, а этот пользователь обычно в группе `docker`. Хук пропускает любую форму команды, которой нет в его шаблонах: например, склейку имени (`cat .en""v`), имя файла в переменной, `echo $ИМЯ_ТОКЕНА`, `base64`, запуск команды из файла. Если хук не запустился, команда выполняется. Бывают ложные отказы (например, на `ls backups/*.dump` или `grep -rn` по папке с кодом): такую команду выполните сами. Копия базы вместе с ключом шифрования раскрывает пароли кабинетов Kaspi. Если такой доступ агенту недопустим, ставьте вручную по путям 1 или 2.

## 4. С помощью автора

Вопросы и ошибки — через Issues репозитория `onezonedata/kaspisa`. Сроков ответа автор не обещает.

Что приложить к вопросу:

- версия (`git describe --tags`) и режим установки;
- вывод скрипта, который не сработал;
- журнал `backups/update-*.log`, если речь об обновлении.

Перед отправкой проверьте журнал и вывод на наличие секретов.

Чего не присылать: файл `.env`, ключ шифрования, пароли, копии базы, cookie сессии.

Автор не просит доступ к серверу и паролям.

## После установки

- Обновление: `bash update.sh <метка>`, см. `docs/deploy.md`, раздел 6.
- Обновление на версию с миграцией `0010` необратимо удаляет записи «Магазин без подключения» (магазины без `merchant_uid` и без товаров). Перед обновлением `update.sh` снимает копию `backups/update-<время>.dump` и называет её имя. Вернуть удалённое можно только из этой копии и только вернув программу на версию без миграции `0010`: `deploy/restore.sh` на новой версии снова применит миграцию `0010` и удалит те же записи.
- Обновление через агента Claude Code — только в интерактивной сессии: запуск `update.sh` требует вашего подтверждения, а в неинтерактивном режиме (`claude -p`) запрос подтверждения отклоняется. В этом режиме команду запускаете вы сами.
- Копии базы и восстановление: `docs/deploy.md`, раздел 5.
- Проверка новой версии (выключена, если `KASPISA_UPDATE_REPO` пуст): `docs/deploy.md`, раздел 7.

## Что не проверено

Проверено на чистом Ubuntu 24.04: строка одной командой (клон из git bundle вместо GitHub), пользователь `kaspisa`, копия ключей, `su -` с группой `docker`, `deploy/prepare-server.sh`, шаги защиты сервера (sshd и `ssh.socket`, ufw, fail2ban, автообновления, уведомление о входе в Telegram), копия и восстановление, обновление в режиме сборки.

Не проверено:

- Ubuntu 22.04 и Debian 12.
- Клон с GitHub: при проверке публичного репозитория ещё не было; сеть до GitHub с сервера не проверена.
- Режим `public` через агента, Let's Encrypt, Tailscale.
- Агент, работающий с сервером по SSH с компьютера владельца.
- Интерактивная установка агентом на сервере: проверены только отказы `claude -p`, запрос подтверждения не проверен.
- Codex: на стенде не установлен.
- Хук закрывает только формы из своих шаблонов, другие формы команд не закрыты.
- Юридическая проверка `LICENSE` и `TERMS.md`.

Подробности по эксплуатации — `docs/deploy.md`, раздел «Что не проверено».
